# Rule 1 - 建立 plan 前先判斷可獨立交付的成果

- Level: `MUST`
- 以使用者成果判斷邊界：某部分不等待其他新功能，仍有完整用途、可驗收且可交付時，視為拆分候選；不把每個 User Story、頁面或技術層各拆成 plan。
- 多個候選成果，或「全站／全面」涉及多模組且具有獨立驗收面時，在建立目錄前向開發者說明候選範圍、獨立價值、真實依賴、納入測試／環境／部署／人工驗收的成本，以及建議順序。提醒應給出具體拆分建議，不能只說 scope 很大。
- 由開發者選擇本輪建立的 plan；已明確要求拆分或合併及指定先做範圍時直接承接，不重複請求確認。尚未選定時只停止建立受影響 plan，不預建全部候選或擅自遺漏需求。
- 單一成果且邊界清楚時直接前進，在 spec 簡記範圍，不新增拆分訪談或獨立審批。task 數、頁數與預估天數不能取代成果判斷。

## Good Example

```md
輸入：旅行刪除／還原、旅行縮圖、全站載入回饋。
建議三份 plan：旅行管理、縮圖、全站回饋；各自列成果與驗收面。
旅行管理可先交付；縮圖依賴既有旅行識別；全站回饋另跨登入、帳目及結算。
開發者選本輪先做旅行管理後，才配置下一個 plan 編號。
單純修正旅行名稱驗證則直接建立一份 plan，不詢問是否拆分。
```

## Bad Example

```md
因為三個功能都出現在旅行頁，直接建立一份涵蓋全部需求的 plan。
或把旅行管理依前端／API／資料庫分成三份無法獨立使用的 plan。
```

# Rule 2 - 合併理由與最低品質邊界必須可追溯

- Level: `MUST`
- 保留多個候選成果於同一 plan 時，記錄開發者選擇、共同交付理由與逐步驗證方式；合理依據包括必須共同上線才成立、拆分需高成本過渡相容、或變更很小而拆分成本明顯較高。
- 共用畫面、程式庫、測試環境或審查人員本身不足以證明必須合併；應比較實際依賴與重複驗收成本。拆分後的共用驗證設施可沿用，但不能沿用已失效的通過證據。
- spec 記錄本輪納入／排除、後續候選及依賴；checklist 核對決定與理由。每份 plan 保留自身必要的正確性、權限、載入、錯誤、恢復與可用性要求，不能把基本品質全推給後續改善 plan。
- 「全站」要求須展開受影響模組與主要驗收面；未收斂時保留缺口並交 `/clarify`，不以全域 NFR 藏入未評估的產品範圍。

## Good Example

```md
旅行管理納入刪除／還原、忙碌防重複、失敗與未知結果恢復。
排除新增縮圖與其他模組狀態統一；全站回饋候選另含登入、帳目及結算。
兩個高度耦合的付款成果經開發者選擇合併，spec 說明共同交易邊界與分段驗證。
```

## Bad Example

```md
旅行管理不處理刪除失敗與重試，等全站回饋 plan 再補。
或只寫「全站載入一致」，未交代涉及哪些模組與驗收面。
```
