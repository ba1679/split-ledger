# Rule 1 - 依風險分配驗證層與環境

- Level: `MUST`
- 本契約統一 research、DSL、tasks 與實作端的測試範圍及人工驗收責任；使用者已確認的政策直接承接，明列來源。新增 plan 採本契約；舊 plan 的明訂範圍由 `/tasks` 或相應 owner 依授權增量調整並保留證據，不能由執行者直接 skip、改 truth 或回寫既有狀態。
- API／單元優先保護帳務精度、分攤、分類、幣別、權限、完整來源與同快照；主要手機 E2E 保護核心旅程、修改後更新、失敗重試、跨旅行／帳號及舊回應競態。各層按獨有失敗模式選案例，不把同一業務排列在每層重演。
- 桌機／第二瀏覽器僅選有具體風險的 smoke 與已知缺陷回歸，例如載入、幣別切換、資訊卡開關、WebKit 焦點／觸控。保留曾發現缺陷的組合，直到有明確替代覆蓋。主要瀏覽器、手機尺寸及輸入方式在 plan 寫明，不把瀏覽器模擬稱為實體裝置驗證。
- 額外尺寸、reduced-motion、輸入方式，只在不同 DOM、事件、焦點、布局或時序責任時加入代表案例；記錄案例／範圍、環境、風險理由與執行入口。執行次數可核對漏跑，但 DSL 句數、檔案數與總次數不能當作覆蓋率，也不能自動展開笛卡兒積。

## Good Example

```md
手機 Chromium：核心旅程與更新／競態。
WebKit 手機：已知 sector touch 與回焦缺陷；桌機：入口、切幣與資訊卡 smoke。
reduced-motion：等待及離線動畫代表案例；其餘尺寸不重演全部帳務排列。
```

## Bad Example

```md
59 個語意案例 × 兩瀏覽器 × 兩尺寸，再把每個案例乘 reduced-motion，沒有額外風險理由。
```

# Rule 2 - 每筆 task 重用適當驗證，新增測試須有獨立價值

- Level: `MUST`
- 一條 DSL 一個 task 是執行粒度，不代表一條 DSL 必須另寫 support spec。先引用能觀察該句的既有 feature focused run、必要前置斷言、型別／契約檢查；產品行為的 RED／GREEN 仍需有效執行訊號，型別檢查不能冒充產品驗收。
- 只有新增獨立失敗模式才另寫 support 測試，例如 response barrier 的攔截／釋放、清理、錯 scope 不被攔截，以及 oracle／assertion 拒絕錯誤結果。必要時以錯金額、漏項或錯旅行證明會拒絕；重用同一 helper／assertion 再跑正確回應不算獨立驗證。
- 判斷合併時讀實際斷言，簡記「獨有前置｜獨有斷言｜替代覆蓋｜保留／合併理由」即可。support 目錄可能包含真正的同快照、取消或敏感資料移除產品整合案例，依其行為判斷，不能整目錄刪除。
- Given 優先沿用真實且穩定的 API／fixture 建態；只有 DSL 明定的保存操作、快取歷史或事件路徑需保留 UI 前序。不得重做產品 oracle 自證、改寫目標 Act 或削弱 DSL。

## Good Example

```md
T084 明細 Then：引用 F04 的 focused run，不另寫相同成功旅程。
barrier support：另驗錯旅行不被攔截、指定請求 release 前未完成及 teardown 清理。
同快照 support：保留受控並行寫入案例，因普通成功 feature 無法替代。
```

## Bad Example

```md
每個 Given／When／Then 都新增一個真 DB＋瀏覽器成功測試；或因在 support 目錄就全部刪除。
```

# Rule 3 - 工程策略有獨立範圍及觸發條件

- Level: `MUST`
- 算術結果、比例誤差有界、無 NaN／Infinity、權限及同快照等正確性持續作為必要檢查。權重尺度如 `10^12` 可作 math 模組的明確技術契約，產品層主要驗使用者可見比例與內容，不在各層重複固定內部表示。
- SQL 查詢數、EXPLAIN、負載與 bundle 等依風險放在現有獨立命令／config，記錄何時重跑、預期證據及是否阻擋交付；已有獨立入口就沿用。repository／演算法改變時重驗相關策略，不要求每個 UI task 重跑工程實驗。
- 策略斷言失敗須評估新策略與證據，不能直接視為產品錯誤；也不能把整份混有正確性要求的工程測試一律改成非阻塞。

## Good Example

```md
修改聚合 SQL：執行既有 cost config，核對結果正確性及成本變化。
只改資訊卡間距：跑對應畫面檢查，不重跑 5000 筆 SQL 實驗。
```

## Bad Example

```md
產品總額正確，但查詢從四次改成三次就直接判產品錯誤；或為省成本忽略同快照失敗。
```

# Rule 4 - 使用者集中人工驗收與自動化狀態分開

- Level: `MUST`
- 桌機完整排版、長內容、視覺品質與完整無障礙（鍵盤、焦點、VoiceOver）交由使用者集中驗收；無障礙仍是產品要求。代理完成必要自查、提供同版證據及簡短驗收包，不必強制操作 VoiceOver，也不逐小 task 要求使用者重驗。已知焦點／觸控缺陷的自動回歸仍依風險保留。
- 驗收包包含可取回產品版本、環境／入口、範圍或畫面 ID、操作步驟、預期結果、已知差異與待確認項目，放在既有 validation／handoff；截圖按可比較資料與尺寸提供，不需為每個組合新建 runner。
- 分別記錄「自動測試通過」「待人工驗收」「使用者已確認」及其版本／範圍／證據。測試政策同意、設計批准或代理自查都不等於使用者已完成產品驗收；產品變更只使受影響的確認失效。
- `/tasks` 將集中人工驗收與自動化 task 分開，列出真正依賴的交付／baseline 關卡。已完成其指定自動化與自查的 task 可回寫，人工 task 維持未完成；只有依賴人工結論的任務等待，其餘獨立工作繼續。所有必要驗收完成前不能宣稱整個 plan 交付，獨立審查與驗收後基準保存照常保留。

## Good Example

```md
手機 Test Scope 全綠，T020 自動化完成；T030 桌機／VoiceOver 驗收包待使用者確認。
獨立 API 工程工作可續跑；依賴 T030 的最終 UI 交付及 baseline 尚未解鎖。
```

## Bad Example

```md
使用者同意手機為主，就把桌機／VoiceOver 標 PASS；或工具不能啟用 VoiceOver 就停止所有獨立 API 工作。
```
