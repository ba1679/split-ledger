# Rule 1 - 按使用者可見影響分流並保存依據

- Level: `MUST`
- 按受影響範圍分類，不以修改前端或後端檔案判斷；同一 plan 可以混合 A／B／C。
- A（沒有 UI 影響）：不改使用者可見資訊、操作或呈現；記錄不適用理由，省略 UI 設計與驗收，完成適用工程驗證。
- B（既有呈現的資料或行為改變）：沿用資訊位置、元件與操作規則；在 `plan.md` 記錄畫面／狀態 ID、路由、既有呈現依據與本次 spec／truth 行為來源。驗證受影響行為，資料長度、狀態或共享元件可能影響呈現時補同尺寸畫面回歸及理由；不新增設計稿或強制建立 `ui/`。程式、現況截圖只證明呈現，不能證明錯誤業務行為正確。
- C（有設計變更）：新增或改變區塊排列、資訊位置、導航、操作入口或可見狀態；進入 `/ui-plan`，取得受影響設計的有效確認後，才進入依賴它的細化與實作。新增錯誤碼需新增錯誤介面也屬 C。
- `/system-analysis` 首次在 `plan.md` 記錄分類、理由、受影響範圍、設計／行為依據及委派；`/tasks` 和實作端依實際範圍核對。單獨 `/bdd` 或 `/implement` 可在 plan-side 紀錄補充分流與依據；缺少 plan 時先建立最小交接紀錄並回報位置，不把分類當成自行補業務規格的授權。
- 發現 B 實際需要改設計時，只把相關範圍升 C 並回交 `/ui-plan`；分類或依據缺口影響驗收意圖時回交規格 owner。只阻擋真實依賴待決事項的範圍，保留其他已驗證進度。

## Good Example

```md
B：結算金額修正；plan.md 引用 settlement/main、既有截圖與新版 truth 計算規則。
沿用原卡片與操作；驗證金額，長金額補手機換行回歸，不建立 ui/。
```

## Bad Example

```md
只改後端，所以新增錯誤 dialog 也分類 A；或因 B 沒有 ui/index.html 就停止。
```

# Rule 2 - 固定基準版本並分開現況與提案

- Level: `MUST`
- `specs/ui-baseline/split-ledger.pen` 描述已實作、已核對並驗收的現況；`README.md` 記錄產品 commit、基準版本、穩定畫面／狀態 ID、涵蓋範圍、已知差異及更新紀錄，`previews/` 保存對應預覽。未實作提案留在 `specs/plans/NNN-*/ui/`。
- 引用固定 repo commit、檔案路徑、畫面／狀態 ID 與同版預覽，不只記可變路徑或版本別名；尚未提交的提案以內容雜湊固定並保存可取回的內容。舊 plan 恢復時從固定 commit 取回必要設計與預覽到獨立檢視位置，不覆蓋現行基準或自動改用最新版。
- 新需求從相關基準 frame 延伸；未修改部分引用原版本，修改部分交付足夠審查上下文。實作依據是固定基準＋本次已確認設計；業務規則仍由 spec／truth owner 決定。
- 基準可逐步建立。C 缺基準時先固定產品版本、核對必要現況；可在 plan-side 記錄核對結果，不必先建全產品基準。B 可先用程式、既有驗收或現況截圖定位呈現。
- `/ui-plan` 一般需求模式只寫 plan-side `ui/**`；明確指定的「建立基準」模式才可建立或更新 `specs/ui-baseline/**`，須固定產品版本並實際視覺核對，不將尚未實作的已批准設計直接升為現況。
- 既有有效確認在其版本與範圍內可沿用；本次新增或改變的設計意圖須確認。基準更新不自動使舊 plan 的固定引用與批准失效；實際整合衝突另按影響重驗。

## Good Example

```md
引用 repo commit a1b2c3d 的 specs/ui-baseline/split-ledger.pen，frame trips/mobile；
同 commit 的 previews/trips-mobile.png。plan 的新 dialog 留在 ui/trip.pen。
```

## Bad Example

```md
用「最新版 baseline」取代舊 plan 引用，或把未實作的 design-v6 當成現行產品。
```

# Rule 3 - C 類設計交付、確認與畫面交接必須可定位

- Level: `MUST`
- C 類交付順序為必要 `.pen`／預覽／行為註記 → 本次設計確認 → 選用互動決策（若有）→ 依賴範圍的 DSL／tasks／實作。設計索引保存在 `ui/ui-plan.md`；A／B 的必要依據留在 `plan.md` 或最小 plan-side 交接。
- `.pen` 由支援格式的工具建立、儲存及檢查，展示可編輯檔連結與桌機／手機預覽。工具不可用時記錄受阻範圍，不能以假副檔名、僅 PNG 或 HTML 替代 C 類可編輯設計。
- 設計須交接資訊責任、區塊順序、導航、操作、字體／顏色／間距、responsive 與 accessibility 行為。桌機／手機主畫面及會改變版面或決策的空白、載入、錯誤、長內容、確認、結果未明狀態，使用必要 frame、共用元件狀態或行為註記覆蓋；重複狀態引用共用規則，不逐排列重畫。尺寸由 plan 指定，中間寬度按規則適配。
- 索引以穩定畫面／狀態 ID 對應固定基準、差異設計 frame、預覽、尺寸／資料、正式路由／元件及 feature／tasks；僅選用互動才列其入口及證據。跨模組影響必須涵蓋帳本、共享導航與元件，不能只按 feature 資料夾選一張主畫面；未規劃 task 可留待綁定，不宣稱下游已就緒。
- 確認紀錄包含設計版本、內容雜湊或固定 commit、frame IDs、範圍、確認者、日期與原回覆或可追溯引用。狀態為 `pending`／`changes-requested`／`approved`；自行審查、沉默或「先做看看」不算批准。既有有效確認引用原證據，不逐次重問。
- 待確認或修改要求只停止依賴該版設計的工作；保存版本與續跑點。基準建立模式同樣展示核對結果、預覽與差異，取得該範圍確認後才宣告建立完成。

## Good Example

```md
cross-device 同時影響 ledger/main 與 navigation：引用兩組 frame 與桌機／手機預覽。
總覽放支出摘要，詳情看份額，結算看淨額；等待新版 navigation 確認只阻擋其依賴。
```

## Bad Example

```md
AI 看過 PNG 就自行 approved；測試需要淨額資料，所以任意加在帳本主頁。
```

# Rule 4 - Prototype 選用與完成狀態分開管理

- Level: `MUST`
- 在 `ui-plan.md` 記錄選用方式（不製作／設計工具點擊連線／局部程式原型）、待確認問題、涵蓋互動／畫面 ID、決策結果與模擬限制。設計與註記足夠時選「不製作」，是合法完成狀態，沒有 prototype 版本或同步前置。
- 只有選用時才追蹤互動狀態 `pending`／`completed`／`stale`、固定版本／入口、對應設計版本、操作證據與決策確認。`completed` 表示指定問題已回答、證據存在、對應設計有效且相關決策已確認；AI 不以原型做完代替尚待使用者的決定。
- 原型只回答指定問題；不要求完整主旅程、所有 frame 的可操作副本、全套響應式、React／HTML 重建、假後端或帳務引擎。選用但有未決問題時只阻擋依賴該問題的範圍。
- 選用互動核對同版設計及指定資料／狀態／尺寸；視覺驗收仍依設計，行為依 spec／truth。未選用畫面無須三方同步。已完成舊原型保留歷史，仍使用的互動才維持有效參照。

## Good Example

```md
不製作：布局與行為註記足夠；design-v2 有效批准後直接交 DSL。
局部程式原型：只驗證分攤輸入的即時回饋，completed；假資料，不證明真實保存。
```

## Bad Example

```md
prototype=不製作，卻標 pending 並要求先補齊每頁 HTML 才能排 tasks。
```

# Rule 5 - 來源衝突與設計改版按範圍處理

- Level: `MUST`
- spec／truth 決定業務規則；固定基準＋本次已確認設計決定呈現；UI 註記補充狀態與適配。既有產品只供重用，不能覆蓋新設計。來源矛盾回交相應 owner，不任選一份過測試。
- AI 可處理自然換行、長內容高度、中間寬度、既定規則的次要重複狀態，以及不改外觀／操作意圖的元件與鍵盤語意；留下差異與比對證據。
- 改主要區塊、資訊位置、排列、導航、層級、操作或生效時機，須提出具體差異與選項，取得開發者確認；業務變更先回交規格 owner。AI／reviewer 不自行接受重大偏差。
- 每個相關畫面記錄固定基準、設計及實作版本與比對狀態 `pending`／`synced`／`stale`；未產出者明寫尚未產出。原型版本只對選用互動存在。
- 改設計意圖時更新相關 `.pen`、雜湊及預覽，將受影響設計設為 `changes-requested`，相關互動／任務／實作證據標為 `stale` 並重新確認、驗證；未受影響批准與進度保留。純文件或不改意圖的小修可保留原批准，記錄理由與新雜湊。
- 被取代產物標歷史；當輪任務引用當輪有效版本，無法同步時列出受阻畫面及依賴。

## Good Example

```md
手機長名稱換兩行：適配高度並記錄證據。
把份額移到帳本：更新受影響設計並重新確認，其他已核對畫面保持有效。
```

## Bad Example

```md
新設計單欄，舊 CSS 雙欄；因既有產品可操作就沿用雙欄並宣告 synced。
```

# Rule 6 - 產品比對與最終 UI 驗收保留完整證據

- Level: `MUST`
- C 類先完成第一組代表畫面的設計自查，再解鎖套用同版型／元件的後續任務；tasks 明列代表畫面與依賴。桌機完整排版、長內容及無障礙依 `testing-delivery.md` 的集中人工驗收責任分開排程，不把使用者尚未確認擴散為所有實作的前置。A 不要求 UI gate；B 完成適用行為與畫面回歸。
- 每個 C 類畫面完成或被其他 feature 改動後，按分工在代表尺寸、可比較資料與狀態下自查固定設計預覽與產品；桌機完整比對集中交付使用者，必要風險 smoke 仍由代理驗證。檢查區塊、資訊密度、導航、卡片排列、字體、顏色、間距、主要操作及關鍵狀態；操作性與無溢出不能代替視覺一致。資料不同需註記，避免把金額／筆數差異當版面缺陷。
- `validation.md` 或既有驗證檔記錄畫面／狀態 ID、基準／設計／實作固定版本、尺寸／資料、預期與產品截圖，以及「設計預期｜實際呈現｜差異與影響｜處理結果／確認依據」。選用互動另附其版本與證據。無差異也寫對照範圍，不只填 PASS。
- 適用的最終 UI 家族 gate 保留一次未參與受審實作的獨立審查，核對跨畫面一致性、產品旅程、關鍵狀態、自查證據及使用者集中驗收的版本／範圍與差異收斂；審查者無須重演整套瀏覽器／尺寸矩陣，也不能代替使用者人工確認。完整產品旅程驗收不代表要先建完整 prototype；早期及逐畫面比對不另增每 feature 的家族 gate。
- 問題由實作者修正再驗；重大設計變更按已載入規則回交。人工狀態及獨立工作依測試交付契約處理；必要驗收未完成、未批准差異或相關版本失效時不能宣稱最終 UI 交付；不改設計／DSL／斷言遷就錯誤產品，也不以功能全綠替代 UI 驗收。

## Good Example

```md
ledger/mobile：390×844 同資料比對，設計卡片上下、實際並排；修正並重拍。
原型不製作；最終 reviewer 仍核對完整產品旅程、狀態與差異清單。
```

## Bad Example

```md
所有按鈕達 44px 且功能測試綠，所以卡片排列與資訊位置不同也宣告驗收完成。
```

# Rule 7 - 驗收後回填基準並核對整合差異

- Level: `MUST`
- `/tasks` 對本次需反映到基準的變更安排回填及獨立審查任務，明列產品驗收依賴、寫入 `specs/ui-baseline/**` 的範圍與證據。只改資料／行為且無設計內容需回填時記錄不適用理由。
- 回填前產品行為、適用畫面與 UI gate 已通過；實作者核對最新基準與本次固定起點，將已驗收的相關 frame／元件、預覽、README 產品 commit／範圍／差異／更新紀錄回填。Git 保存歷史，不把未驗收提案混入基準。
- 多個 plan 更新同一基準時，整合非重疊成果並重驗受影響部分；同畫面／共享元件衝突回交相應 owner，不以舊整檔覆蓋最新成果。回填若改設計意圖，重新確認及產品驗證。
- 回填實作任務以更新及自查完成，解鎖獨立核對任務；後者由未參與該回填實作的審查者核對產品版本、設計、預覽與索引一致後完成。適用回填或審查尚未完成時，plan 保持未完成。此任務不擴大一般 `/ui-plan` 或 `/bdd` 的寫入權限。

## Good Example

```md
產品驗收 → 回填 trips/dialog（保留其他 plan 的 ledger 修改）→ 獨立核對 → plan 完成。
舊 plan 仍引用原 commit；不改寫舊批准證據。
```

## Bad Example

```md
產品剛開始做就將提案升 baseline；或回填時用舊 .pen 覆蓋其他已驗收畫面。
```
