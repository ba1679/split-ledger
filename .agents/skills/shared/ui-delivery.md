# Rule 1 - .pen 先交付並取得開發者明確確認

- Level: `MUST`
- 適用於新增或修改 UI 的 plan；無 UI 影響時記錄不適用，不要求無關產物。既有 plan 缺少本契約時先補交付與確認證據，不把歷史 `[X]`、既有畫面或舊 prototype 當作設計已確認。
- 順序是 UI plan／畫面索引 → 可編輯 `.pen` 與預覽 → 開發者明確確認 → 可操作 prototype 與同步檢查 → 前端 DSL／tasks → 實作 → 畫面與行為驗收。純後端且不依賴 UI 決策的工作可獨立進行。
- 在 `ui/ui-plan.md` 記錄設計版本、檔案內容雜湊或固定 commit、frame IDs、確認範圍、確認者、日期與原回覆或可追溯引用。狀態只用 `pending`、`changes-requested`、`approved`；自行審查、沉默或「先做看看」不算批准。
- `.pen` 必須由支援該格式的設計工具建立、儲存與檢查；交付 `.pen` 連結和開發者可見的桌機／手機預覽，不能只有文字宣告完成。工具不可用時記錄阻礙，不能用假副檔名、僅 PNG 或 HTML 替代可編輯檔。
- 待確認時停止 prototype 與依賴該版設計的下游工作；跨 session 仍保持待確認。開發者要求修改時重新交付並等待。既有確認只對記錄的版本／範圍有效，依 Rule 3 判斷是否失效。

## Good Example

```md
design-v1 / trip.pen SHA256=實際雜湊 / ledger 桌機、手機及關鍵狀態
pending：展示可見預覽並請開發者確認，保存續跑點，prototype 尚未開始。
收到「確認 design-v1，可以做 prototype」後記錄原回覆，改為 approved。
```

## Bad Example

```md
已匯出 PNG，AI 自認設計通過；直接寫 prototype 並讓 tasks 解鎖。
```

# Rule 2 - 每個受影響畫面都具備可定位的設計與操作交接

- Level: `MUST`
- `.pen` 涵蓋所有受影響畫面的桌機／手機主畫面，定義資訊責任、區塊順序、導航、主要操作、字體／顏色／間距及響應式規則。尺寸由本 plan 指定；中間寬度按規則適配。
- 會改變版面或決策的空白、載入、錯誤、長內容、確認、結果未明等狀態提供補充 frame 或元件狀態；重複狀態用共用規則與覆蓋對照，不要求每個排列都畫一頁。狀態不適用時說明原因。
- 畫面索引保存在 `ui/ui-plan.md`，以穩定畫面／狀態 ID 對應 `.pen` 檔／frame、預覽、尺寸／假資料、prototype 路徑／狀態入口、正式路由／元件、相關 feature／tasks。尚未規劃的 task 可先留待綁定，但不能宣稱下游已就緒。
- prototype 承接同版設計並可操作主旅程、表單驗證、確認／取消和關鍵回饋；可用假資料，記錄模擬限制及未涵蓋項，不接正式後端也不假稱已驗證真實保存。
- 下游每個 task／feature 必須引用所有實際影響畫面的 ID、設計 frame／預覽與 prototype 入口，包含跨模組修改的帳本、導航、共用元件。不要依 feature 的資料夾名稱只給一張主畫面，也不必載入無關設計。

## Good Example

```md
cross-device feature 修改 TripLedger 與 AppShell：引用 ledger、navigation 的設計與狀態。
總覽只顯示支出摘要；沿連結進詳情檢查份額；結算頁檢查成員淨額。
```

## Bad Example

```md
跨裝置 feature 位於 members 模組，所以只讀 members PNG；為過測試在帳本新增整塊淨額卡。
```

# Rule 3 - 版本同步、來源衝突與 AI 調整權限

- Level: `MUST`
- 業務規則由 spec／truth owner 決定；`.pen` 是已確認的視覺依據，prototype 示範同版互動，UI plan 補充狀態與響應式規則。既有程式可供重用，但不能自動覆蓋已確認設計；來源矛盾時回交相應 owner，不任選一份過測試。
- AI 可處理自然換行、長內容高度、中間寬度適配、既定規則的次要重複狀態，以及不改外觀／操作意圖的元件與鍵盤語意實作；以差異紀錄說明並比對證據，不必逐項詢問。
- 新增／刪除／移動主要區塊、改變導航、資訊位置、排列意圖、視覺層級、主要操作或業務行為，須整理具體差異與選項，由開發者確認後才能採用；AI／reviewer 不得自行接受這類偏差。
- 每個畫面記錄 `design-version`、`prototype-version`、`implementation-version` 與同步狀態 `pending`／`synced`／`stale`，版本以 commit 或內容雜湊固定；未產生的欄位明寫尚未產出。實作前要求設計批准有效、prototype 對應同版且 `synced`、重大待決差異為零。
- prototype／實作發現設計問題時，先記錄並回交；改變設計意圖則更新 `.pen`、版本及預覽，將受影響範圍設為 `changes-requested`、下游設為 `stale` 並重新取得確認，再同步 prototype／任務／測試與實作。業務變更先回交規格 owner。純文件或不改意圖的小修可保留原批准並記錄依據與新雜湊。
- 替換後的舊產物標示歷史版本，任務只連到目前版本。無法同步時列出受阻畫面及依賴，不讓舊 prototype 繼續當作當輪交付。

## Good Example

```md
手機字串自然換兩行：AI 修正高度並留下比對。
要把份額從詳情移入帳本：提交差異請開發者決定，更新設計後重新同步受影響畫面。
```

## Bad Example

```md
設計已改成單欄，但 prototype 還是雙欄；因既有 CSS 也是雙欄就照舊做並宣告同步。
```

# Rule 4 - 逐畫面比對與最終驗收必須可追溯

- Level: `MUST`
- 第一個代表性畫面完成桌機／手機後先做設計比對，再解鎖套用同版共用版型／元件的後續畫面；tasks 選定代表畫面與依賴，不等全部前端完成才檢查。
- 每個畫面完成或被其他 feature 改動後，在指定尺寸、可比較的資料與狀態下比對設計預覽／prototype／實際產品；資料不同時標明差異，不把金額或筆數差異誤當版面缺陷。檢查區塊、信息密度、導航、卡片排列、字體、顏色、間距、主要操作與關鍵狀態，操作性／無溢出不能代替視覺一致。
- 在 plan 的 `validation.md` 或既有驗證檔記錄畫面／狀態 ID、三方版本、尺寸／資料、設計與實際截圖路徑，以及「設計預期｜實際呈現｜差異與影響｜處理結果／確認依據」。沒有差異也寫明對照範圍；不能只寫 PASS。
- 最終 UI 家族 gate 保留一次獨立審查，檢查跨畫面一致性、完整旅程、關鍵狀態及差異收斂。逐畫面比對與早期 checkpoint 是實作完成證據，不另按每個 feature 建立獨立家族 gate。
- 有問題由實作者修正並重查；必要設計變更依前條同步與重新確認。不得改設計、DSL 或斷言來遷就錯誤產品。未驗證、未批准差異或同步失效時不能交付；保留限制，不以功能測試全綠代替 UI 驗收。

## Good Example

```md
ledger/mobile-v1：預期卡片上下排列，實際並排；已修正，附同資料 375px 重拍證據。
最終 reviewer 核對各畫面版本與旅程，再回報無未決差異。
```

## Bad Example

```md
44px 觸控與無水平溢出都通過，所以即使多出淨額區塊仍宣告設計完全一致。
```
