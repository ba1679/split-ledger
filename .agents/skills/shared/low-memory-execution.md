# Rule 1 - 在入口選定模式並傳遞同一份資源契約

- Level: `MUST`
- 使用者指定低記憶體模式、可觀測實體記憶體不超過 16 GiB，或無法判定容量時，選用 `low-memory-16gb`。容量較大且未受記憶體壓力影響時可使用 `standard`；使用者明確指定的模式優先，但不得忽略已觀察到的資源告警。
- 契約記錄 `profile`、實體記憶體或未知、主代理／輔助代理角色與 ID、保留代理上限、同時重型工作上限、測試 worker 上限、瀏覽器順序、基線、程序登記位置及可用關閉／重置能力。
- `implement` 把契約交給 `bdd` 與審查者；下游使用同一份全域預算，不各自增加名額。單獨執行 `bdd` 時由目前代理建立契約。
- 本檔是兩個 skill 的資源規則單一溯源，路徑相對於各自 `SKILL.md` 為 `../shared/low-memory-execution.md`。這是一般參照文件，不是需要另外啟動的 skill。若文件缺失，回報缺漏並停止新增代理／重型工作，不另猜一套限制。

## Good Example

```md
profile=low-memory-16gb；RAM=16GiB
主代理負責實作；固定輔助代理只做獨立審查。
下游 bdd 承接同一契約，未另外取得測試代理名額。
```

## Bad Example

```md
implement 限制一個工作者；每個 bdd 工作者再各自建立測試與瀏覽器代理。
```

# Rule 2 - 低記憶體模式控制保留總量並逐筆排程

- Level: `MUST`
- `low-memory-16gb` 最多保留主代理加一個輔助代理，包含閒置代理；同時最多一個重型工作，例如測試 runner、build 或型別檢查。輔助代理不得再建立子代理。
- 優先由主代理直接實作並在目前上下文載入所需 skill，固定輔助代理專責獨立審查。沿用既有代理時重新交付目前 task／scope／requested step，不沿用舊任務的完成結論。
- 每輪恰好一個已解鎖 task。`[P]` 與 `Parallel Hint` 保留可平行與批次 review 的資訊，低記憶體模式依 Dependencies 逐筆實作、驗證、回寫；整批完成後才進入原 review 關卡。
- 不因每筆 DSL、BDD 入口、測試命令或 review 重跑就新建代理。只有舊輔助代理的資源已確認退出且預算容許時，才可替換；無法回收時不得持續累積替代者。
- `standard` 也先記錄有限的代理與重型工作預算，才派出預算內已解鎖批次；需要分波時保留原批次 review 邊界。

## Good Example

```md
Hint 列出 T008–T014：同一實作者逐筆處理，每筆測試通過立即打勾。
七筆皆完成後，固定審查者檢查整批；不提前啟動 Green。
```

## Bad Example

```md
同時只跑兩個代理，但每完成一筆就新增下一個代理，保留所有舊工具環境。
```

# Rule 3 - 獨立審查以未參與實作為準

- Level: `MUST`
- 需要獨立審查時，由沒有實作受審改動的另一個代理執行；主代理自行跑測試不能代替獨立審查。固定審查者可重用，但每輪必須讀取最新 diff、指定規格與實際驗證證據。
- 審查者回報 findings，由實作者修正後再交回審查；審查者不直接修補自己正在審查的改動。全部問題收斂前保留原 review gate。
- 若唯一輔助代理已參與受審改動，必須先完成可驗證的釋放，再建立未參與實作的替代審查者。工具無法釋放時保存進度並回報審查受阻，不以自審、額外常駐代理或略過 gate 補位。

## Good Example

```md
主代理修改 T012；固定審查者只讀 diff 與測試結果，提出兩個問題。
主代理修正，原審查者重新檢查，直到 zero open findings。
```

## Bad Example

```md
為了少用記憶體，讓寫入 T012 的同一代理宣告自己的獨立審查通過。
```

# Rule 4 - 在資源檢查點判斷可否繼續擴張

- Level: `MUST`
- 入口建立基線；每次派工或啟動重型工作前、每筆 task／BDD slice 結束後，檢查受管工作、程序數與記憶體壓力。比較長期趨勢，不只看同時執行中的代理數。
- 使用平台與工具實際提供的量測。macOS 可讀 `sysctl hw.memsize`、`vm_stat`、`sysctl vm.swapusage` 與 `ps`；程序列表應限制為 PID、父 PID、RSS、啟動時間與程式名稱，避免輸出憑證。其他平台沿用可用的等價資訊。
- 登記自己啟動的 session／PID、父程序、啟動時間與用途；瀏覽器的多程序結構不等於多個測試 worker。RSS 可能包含共享頁，不能把所有程序 RSS 相加當作實體記憶體用量。
- 記憶體壓力警告／critical、OOM／系統終止事件，或無法對應受管工作的工具程序持續增加，均視為資源檢查未通過；swap 持續增加時須配合壓力與程序趨勢確認，不能只因 swap 非零就判定故障。
- 未通過時停止新派工與新重型工作，先回收受管資源並重測。無量測權限時記錄「未知」，沿用低記憶體硬上限與可驗證的工作結束資訊；不得宣稱已證明記憶體穩定。若連工作是否結束都無法確認，保存續跑點並回報限制。

## Good Example

```md
前一筆測試已退出，但每筆後 node_repl 數量仍上升且沒有受管工作對應。
停止建立新代理，檢查工具環境是否可回收，而非繼續下一百筆。
```

## Bad Example

```md
目前只有一個瀏覽器測試，所以不檢查其餘兩百個工具程序。
```

# Rule 5 - 以實際退出證據確認回收

- Level: `MUST`
- 測試的 fixture／context／browser／server 使用既有 teardown、finally 或工具關閉能力；命令完成後核對退出狀態與本輪登記的子程序。需要常駐的服務須記錄有限名額與用途並重用。
- 代理回覆完成、`interrupt`、停止輪詢或關閉畫面，都不能當作 OS 程序與工具環境已釋放的證據。優先使用環境真正提供的關閉／重置 API，再重新量測。
- 分別記錄命令已退出、可歸屬的子程序已退出、工具環境回收未知三種證據；無法把 agent ID 對應 PID 時明列未知，不要求捏造 OS 對應。固定審查者可在階段 checkpoint 交接更新上下文，但替換仍受可用關閉能力與保留總量限制；無法回收時保存交接，不累積替代者。
- 僅可處理已確認屬於本輪、且 PID 與啟動時間／父程序仍匹配的資源。先正常關閉；不得使用全域 `pkill node`、殺掉所有瀏覽器，或關閉使用者既有應用程式。
- 回收採有界等待，例如兩次各五秒檢查。工具缺少關閉能力、程序未退出或壓力持續時，保存阻礙與續跑點，不反覆新建代理、無限等待或承諾已回收成功。

## Good Example

```md
runner exit=0；本輪 API server 與 browser 子程序已結束。
工具管理的 REPL 無關閉 API 且數量仍增加：記錄限制，停止擴張並交付續跑資訊。
```

## Bad Example

```md
subagent 已回覆完成，所以假設工具記憶體已清除；繼續 spawn 下一個。
```

# Rule 6 - 降低並行度並保留完整驗證矩陣

- Level: `MUST`
- 低記憶體模式直接使用既有 runner 執行測試，worker 上限為一；一次只跑一個瀏覽器 project／重型命令，上一個結束並完成回收檢查後才啟動下一個。測試執行不需要新增代理。
- 開發迴圈沿用最窄有效 focused 測試；Green 完成仍覆蓋指定 `Test Scope`，重構與 NOOP 的影響判斷及證據重用依入口載入的共用測試證據判準。最終交付保留 plan／專案要求的完整回歸、瀏覽器與檢查，不用抽樣、縮減案例或 skip 換取低用量。
- 建立完整矩陣的執行帳：範圍、瀏覽器／環境、預期案例數、命令、退出狀態、通過／失敗／跳過數與 log 路徑。可依 feature、瀏覽器或既有 shard 依序執行；合併結果須覆蓋全部要求且無遺漏或重複計數。
- 資源不足而未跑的項目標記待執行；測試中止或逾時不能算通過。不以累加數次不同程式版本的部分成功結果代替完整回歸；程式或環境改變後重跑受影響項目，無法判定影響時重跑完整矩陣。

## Good Example

```md
完整 scope：12 Examples × Chromium/WebKit = 24 executions。
先以既有 runner 的 workers=1 跑 Chromium 12，再跑 WebKit 12。
兩邊完成、案例集合一致、沒有 skip，才回報 scope 全綠。
```

## Bad Example

```md
只跑 Chromium 三個抽樣案例，因電腦只有 16GB 就宣稱完整回歸通過。
```

# Rule 7 - 保存可續跑進度並維持完成判準

- Level: `MUST`
- 在 plan 既有驗證紀錄或專案約定位置保存資源契約、最近檢查點、目前 task／slice／requested step、程式版本／未提交 diff、已完成與待跑矩陣、log 路徑、審查 findings、受管程序及停止原因。
- 每筆 task 的實作與驗證完成後才可回寫 `[X]`；原本的單步 BDD、Phase 3 不寫產品碼、獨立 review gate 與最終完整回歸要求維持不變。
- 資源回收受阻只代表暫時無法續跑，不代表任務或 plan 完成。恢復時先核對 Git／環境、資源基線、已完成項目證據與未完成關卡，再從第一個已解鎖 task／待跑矩陣續跑。
- 正常 session checkpoint 與精簡交接欄位由入口讀取的 `session-handoff.md` 統一管理；不必等記憶體失敗才交接，也不重複貼整份歷史輸出。

## Good Example

```md
T012 已驗證並打勾；T013 尚未執行。review 仍未解鎖。
因工具程序無法回收停止，保存上述進度；恢復後由 T013 開始。
```

## Bad Example

```md
因記憶體不足，把尚未跑的 WebKit 與 review 一起標成完成。
```

# Rule 8 - 完整證據落檔並限制聊天輸出

- Level: `SHOULD`
- 完整 runner 輸出、trace、截圖與盤點結果存入專案約定的 log／暫存位置；聊天回傳範圍、結果、必要錯誤摘要及檔案路徑。
- 重用必要的工具環境，按任務載入上下文。大型報告與圖片不反覆貼入各層代理；資源檢查直接使用短命令，不為監控另外啟動常駐 agent 或 daemon。

## Good Example

```md
回報：WebKit 12/12，exit 0，log 位於既有驗證目錄。
```

## Bad Example

```md
為每一筆 DSL 建立一個監控代理，並在每層貼入完整 trace 與所有截圖。
```
