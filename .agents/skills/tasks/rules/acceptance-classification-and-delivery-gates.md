# Rule 1 - 每項驗收依性質對應證據

- Level: `MUST`
- 產品介面行為新增或改變須由 truth feature / DSL 唯一承接；缺漏時回交 `/dsl-refine`，不得改標工程任務繞過。
- 純重構的行為不變需求引用受影響既有測試回歸；列出具體範圍與執行入口，並依需要加入工程或視覺檢查。測試不足時明列補足或替代驗證及限制，不宣稱既有測試已覆蓋。
- 工程交付與人工確認直接回追 spec / plan 對應項目，列出交付物、檢查方式、通過條件及證據；不虛構產品介面。
- 無受影響 DSL 需對齊時省略空 Phase 3，說明原因；混合需求的產品行為仍遵循原 BDD 流程。

## Good Example

- 重構引用回歸，工程檢查另有證據。

```md
T010 遷移表單，回歸既有表單 feature；檢查移除的 CSS 無引用。
```

## Bad Example

- 用工程檢查代替新增產品行為規格。

```md
新增送出行為，但只檢查 CSS 並略過缺失的 feature。
```

# Rule 2 - 使用者確認關卡須有可執行依賴

- Level: `MUST`
- 僅依需求中明確的確認要求建立 `[USER-CONFIRM]` 任務，列來源、待展示成果與證據、確認對象、通過條件、前置任務及受阻任務。
- 不得標成平行任務；下游任務明列依賴此關卡。不影響其他可獨立執行的任務。
- 使用者未確認或要求修改時，關卡維持未完成；修改並重新展示後才可再次確認。

## Good Example

- 依賴與確認條件明確。

```md
T011 [USER-CONFIRM] 展示 T010 的遷移前後畫面；使用者確認可繼續後通過。
T012 遷移其餘畫面；Dependencies: T011。
```

## Bad Example

- 缺乏確認者及受阻依賴。

```md
T011 看起來沒問題就完成，繼續所有遷移。
```
