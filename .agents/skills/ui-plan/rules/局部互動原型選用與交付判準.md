# Rule 1 - 原型範圍由待確認問題決定

- Level: `MUST`
- 選用方式、狀態及下游前置依主 SOP 已載入的共用 UI 契約；本規則只約束選用互動的製作品質。
- 對每個互動指出「需要體驗才能決定什麼」、相關畫面／狀態 ID、輸入、操作、預期回饋及決策者；設計與行為註記足夠回答時交回不製作。
- 導航、dialog、步驟轉換優先用設計工具連線；動態輸入、拖曳或即時回饋確實影響決策時才局部寫程式。工具不支援所需連線時記錄能力限制，選擇能回答該問題的最小替代方式。
- 只模擬判斷必要的上下文與狀態，不建立全套頁面、全尺寸切版、假後端或帳務引擎；不固定 index.html 入口，入口可為指定 frame 或局部檔案。

## Good Example

```md
問題：取消 dialog 是否保留上一步輸入？
用相關 frame 的連線示範開啟／取消／返回，其他頁面引用設計即可。
```

## Bad Example

```md
只需判斷一個取消操作，卻重建整套旅行帳本、計算引擎與響應式網站。
```

# Rule 2 - 指定互動必須可操作且揭露模擬限制

- Level: `MUST`
- 指定問題所需的點擊、輸入、拖曳、取消、驗證或結果回饋須可實際操作；依問題選必要子集，不要求每個原型涵蓋完整流程。不能用不可操作截圖宣稱互動已驗證。
- 使用對應設計版本、指定資料／尺寸／狀態操作並記錄結果、差異、決策與證據；只核對選用互動。已批准設計有意圖改變時回交，不以原型反向覆蓋設計。
- 可使用假資料或固定結果，明示未涵蓋的保存、連線、權限、計算或第三方行為；未串正式後端不能宣稱真實保存或帳務已驗證。
- 畫面只呈現產品內容，例如標題、欄位、CTA、狀態與錯誤；元件樹、TODO、工程解說與 reviewer 備註留在 ui-plan／驗證文件。局部原型可省略無關畫面，但仍保留問題所需真實操作語意。

## Good Example

```md
只操作 split/input 的即時回饋，取消返回保留輸入；記錄同版設計與操作證據。
固定兩位成員資料，不驗證正式儲存及帳務結果；決策已由指定者確認。
```

## Bad Example

```md
把按鈕截圖稱為可操作；寫「TODO 呼叫 API」在產品畫面，並宣稱假資料保存已驗證後端。
```
