# Rule 1 - 平行許可以資源契約為上限

- Level: `MUST`
- `[P]` 與 `Parallel Hint` 是可平行與批次審查資訊；實際任務集依已載入資源契約收斂。
- 低記憶體模式每輪一個已解鎖 task；標準模式才在預算內採 Hint 批次或分波派工。未標 `[P]` 的序列 task 不得併批。
- Hint 的排程、單筆 handoff 與整批 review 另依已載入的 Parallel Hint 規則；資源降載不移除任何 task 或 review。

## Good Example

```md
低記憶體模式依序完成 Hint 內各筆，全部完成才 review。
未標 [P] 的 Green 與 Refactor 維持不同輪。
```

## Bad Example

```md
把「可平行」當作必須同時啟動所有代理，或為省資源合併序列 Green／Refactor。
```

# Rule 2 - 共享修改面保留序列與寫入端合併責任

- Level: `MUST`
- Feature phase 或非 Phase 3 task 若修改同一檔案、同一模組邊界，或依賴尚未穩定的驗證結果，必須序列執行。
- Phase 3 在低記憶體模式同樣序列；標準模式同檔採單一寫入者及序列整合；不以「寫前再讀」當作避免競態覆蓋的保證。
- 有明確整合 task 時，前置 task 完成後才交付整合；reviewer 不代替寫入者合併或修正。

## Good Example

```md
Phase 3 低記憶體模式：T008、T009 先後修改 helper，各自驗證。
Feature phase：共用 store 的 Green tasks 仍依序完成。
```

## Bad Example

```md
為了加速讓兩個 Feature Green 同時改 store，交給 reviewer 處理最後衝突。
```

# Rule 3 - 個別驗證不能被批次結果取代

- Level: `MUST`
- 每個 task 都必須有自身實作與驗證證據後才回寫 `[X]`，序列或平行排程皆相同。
- Phase 3 各波全部對齊後，由該波明列的 review task 承擔收斂與獨立審查；未分波的舊 tasks 仍由原全批 review 承擔，不臨時縮小關卡。

## Good Example

```md
首波 T011–T013 各自驗證、回寫，全部完成後才執行本波 review。
只解鎖本波 Green；後波測試仍須完成自己的對齊與 review。
```

## Bad Example

```md
只測 T008，就把整個 Hint 標成完成。
```
