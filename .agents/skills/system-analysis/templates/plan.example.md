**結構決策**: 採用 `frontend/`、`backend/` 與第三方金流整合並存的 Web 應用結構。前端負責方案展示、結帳流程與付款結果回饋；後端負責建立訂單、發起金流請求、驗證 webhook 並開通訂閱；金流端以第三方服務承接實際刷卡與付款狀態通知；資料庫則持久化使用者、訂單、付款與訂閱狀態。

## 交付依賴與首條驗證路徑

- 本輪交付邊界與後續候選依賴：付款與訂閱開通共同完成結帳成果；不納入行銷活動及跨站視覺改版。
- 首個可獨立驗證成果與正式測試路徑：先以一筆付款成功與訂閱再讀的正式驗收路徑取得回饋，再展開失敗、重試與結果恢復；所需前置若可獨立驗證，由 `/tasks` 排早期產品波次。
- 資料／API／fixture 前置及 owner 待決事項：API／data owner 收斂訂單、付款及訂閱責任後，提供對應正式測試可用的資料建態與狀態查詢依據；本分析尚不定義欄位或假設 migration 已完成。
- 執行環境、瀏覽器／裝置及人工驗收需求：核對金流測試環境與回呼通路、測試帳號、既定瀏覽器及手機驗收安排；前端驗證承接已確認設計，尚未實際執行的項目保持待驗。

## 分析流程規劃

### 系統介面的盤點

本次需求共盤點出 `4` 個系統介面。

1. `前端訂閱與結帳介面`
   - 端點類型：`前端端點`
   - 主要介面：方案列表頁、訂閱方案選擇、結帳表單、付款結果頁、失敗重試與狀態提示
   - 需求原文依據：需求要求「使用者可以瀏覽訂閱方案」、「使用信用卡付款」、「付款失敗時要顯示可理解錯誤並允許重試」、「付款成功後立即看到開通結果」。

2. `後端訂單與訂閱 API 介面`
   - 端點類型：`後端端點`
   - 主要介面：建立結帳訂單、啟動付款流程、接收付款完成結果、開通訂閱權限、提供前端查詢付款與訂閱狀態
   - 需求原文依據：需求要求「付款成功後立即開通會員權限」，且系統需要有可追蹤的訂單與付款狀態，才能支撐成功、失敗與重試流程。

3. `第三方金流服務介面`
   - 端點類型：`金流端點`
   - 主要介面：刷卡結帳頁、付款狀態回傳機制、Webhook 通知、第三方 API 文件與整合限制
   - 需求原文依據：需求要求「使用信用卡付款」，代表系統必須依賴外部金流服務處理實際收款，而付款成功或失敗都會受到第三方介面能力與限制影響。

4. `訂單與訂閱持久化介面`
   - 端點類型：`資料庫端點`
   - 主要介面：使用者、訂單、付款紀錄、訂閱方案、訂閱狀態與重試相關資料欄位
   - 需求原文依據：需求要求「後台查得到訂單與付款狀態」以及「付款成功後立即開通會員權限」，代表系統必須把付款與開通結果可靠地持久化，才能支撐查詢、對帳與狀態恢復。

### 分析流程的安排

#### Wave 1

- 平行分析介面：
  - `前端訂閱與結帳介面`
  - `第三方金流服務介面`
- 分析重點：
  - 前端分析先聚焦 UI/UX 界面、使用者從選方案到送出付款的操作路徑、成功與失敗狀態、重試入口，以及哪些資訊必須在畫面上被清楚揭露。
  - 金流端分析則聚焦第三方文件、可用 API、Webhook 規格、付款頁責任邊界、回傳欄位、錯誤碼與整合限制，必要時先下載文件或整理介面契約。
- 安排理由：前端幾乎是所有需求最早可見的入口，先把 UI/UX 與使用者流程分析清楚，後續再分析後端時會更容易決定 API 形狀與錯誤回饋；金流端與內部系統的耦合相對較低，通常可以獨立從第三方文件先行展開。因此兩端可在資源預算內分析，先收斂使用者需要的呈現與第三方提供的能力。

- 決策依賴、來源與就緒／受阻範圍：第三方文件分析不依賴設計批准，可先交 /api-plan；前端設計由 /ui-plan 承接，待明確確認。不把第三方已完成當成整個 Wave 1 已完成。

#### Wave 2

- 平行分析介面：
  - `後端訂單與訂閱 API 介面`
  - `訂單與訂閱持久化介面`
- 分析重點：
  - 後端分析聚焦如何承接前端流程與金流回傳，設計建立訂單、啟動付款、接收 webhook、狀態查詢、訂閱開通與失敗補償等責任邊界。
  - 資料庫分析聚焦為上述流程提供可持久化的資料模型，包含訂單生命週期、付款狀態、訂閱狀態、重試紀錄與對帳欄位。
- 安排理由：後端與資料庫的分析高度依賴 Wave 1 先收斂出的兩類結果，也就是前端真正需要哪些互動與狀態，以及金流端到底提供哪些 callback、欄位與限制。等這些外圍介面明朗後，再一起分析後端與資料庫，才能避免 API 設計與 schema 建模過早假設錯誤，可在兩者不互等具體結論的範圍內依資源預算安排分析。

- 決策依賴、來源與就緒／受阻範圍：建立訂單及狀態分析依賴 Wave 1 流程與第三方限制；若第三方 webhook 驗證責任已明列且可獨立確定，可先分析該子範圍，仍保留結帳相關設計依賴，不能宣稱整個後端就緒。
