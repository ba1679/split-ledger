## 要落地的政策

### 自動化範圍

- API／單元：優先保護帳務、分攤、分類、幣別、權限及同快照。
- E2E：主要手機環境覆蓋核心旅程、修改後更新、失敗重試、跨旅行／帳號與舊回應競態。
- 桌機／第二瀏覽器：只選少量有具體風險的 smoke／已知缺陷回歸，例如載入、幣別切換、資訊卡開關、WebKit 曾發現的焦點或觸控問題。不再預設全部行為乘所有瀏覽器與尺寸。
- reduced-motion、輸入方式、邊界尺寸：只有不同 DOM、事件、焦點、布局或時序責任時增加代表案例，不預設全面笛卡兒積。
- 不將測試總數、DSL 句數、檔案數當成覆蓋率或必要工作量。

### 人工驗收

- 桌機完整排版、無障礙完整檢查（鍵盤、焦點、VoiceOver）、長內容與視覺品質交由使用者集中驗收。
- 無障礙仍是產品要求，改變的是驗證方式，不是移除要求。無須強制代理操作 VoiceOver 才能繼續所有獨立工作。
- 提供可取回的產品版本、環境、簡短步驟、預期結果、已知差異與待確認項目；不要每個小 task 都要求使用者重驗。
- 區分「自動測試通過」「待人工驗收」「使用者已確認」；使用者同意測試政策不等於已完成產品驗收。只有真正依賴人工結論的交付關卡等待，不擴散阻塞無關工作。
- 保留設計批准、適用獨立審查與 baseline 保存責任；避免藉本次精簡任意刪除其他品質關卡。

### 重用與重複測試判準

- 一條 DSL 的 task 可由既有 feature 的 focused run、型別／契約檢查或必要前置斷言證明，不天然需要新 support spec。
- 只有新增獨立失敗模式時，才另寫 support 測試；response barrier、清理、錯誤 scope 不被攔截、oracle 拒絕錯誤結果等是合理候選。
- 不因檔案位於 support 就刪除；其中可能是真正同快照、取消或敏感資料清除的產品整合案例。
- 合併判斷需看實際斷言：獨有前置、獨有斷言、替代覆蓋、保留／合併理由。先採簡短記錄，不新建龐大管理系統。
- oracle／assertion 的可信度，必要時用刻意錯誤的金額、漏項或錯 scope 證明會拒絕；單純再跑一次正確產品回應不算獨立驗證。
