# 系統分析規劃

## 專案結構

### 文件結構（本功能）

```text
specs/plans/003-design-system/
├── spec.md
├── research.md
├── truth-delta.md
├── plan.md
├── features/acceptance/design-system-migration.feature
```

### 原始碼結構（儲存庫根目錄）

```text
apps/web/src/
├── app/                        # 應用入口與路由
├── components/                 # 共用介面、圖示與日期選擇器
├── features/                   # 登入、旅行、分類與支出介面
├── styles.css                  # 現有全域樣式
└── api/                        # 既有 API 呼叫
apps/api/                       # 既有後端，非本次變更目標
specs/truth/                    # 現行系統規格與技術堆疊
```

**結構決策**: 沿用既有 React 前端及共用元件邊界；本次聚焦樣式、視覺 token、圖示與介面元件。API 和資料持久化是既有流程依賴，本次不要求改動其契約或模型；實作時若發現需要改動，須回到分析重新評估。

## 分析流程規劃

### 系統介面的盤點

本次需求共盤點出 `1` 個系統介面。

1. `前端介面與共用設計系統`
   - 端點類型：`前端端點`
   - 主要介面：登入、旅行、支出與分類畫面，共用元件、圖示、響應式呈現、互動狀態及維護者使用設計基礎的方式。
   - 需求原文依據：FR-001 至 FR-006 要求共用設計值與元件、套件圖示、先示範確認後遷移其餘介面；NFR-001 至 NFR-003 要求保留既有外觀、操作、可存取性與狀態回饋。
   - 委派：`/ui-plan`，分析畫面、互動、共用視覺與示範範圍。

既有後端 API、資料庫、登入服務與所選前端套件是受影響流程的依賴或技術工具，需求未要求改變 API 契約、資料責任或第三方整合，因此不虛列為本次待分析介面；既有 truth 仍是 UI 回歸基準。

### 分析流程的安排

#### Wave 1

- 分析介面：`前端介面與共用設計系統`
- 分析重點：盤點既有畫面與互動，選擇能展示共用元件、設計值及圖示的代表性區塊；規劃現況對照、鍵盤與手機呈現、新舊樣式共存風險，以及示範獲使用者確認後的其餘範圍。
- 安排理由：只有一個本次變更的介面責任，無其他需先完成的 API 或資料設計。此 Wave 是分析排序；使用者確認示範是後續實作遷移的必要節點，不表示本輪分析要先做全站實作。
- handoff：plan package `specs/plans/003-design-system/`；truth root `specs/truth/`；truth delta `specs/plans/003-design-system/truth-delta.md`；目標 `/ui-plan`。
