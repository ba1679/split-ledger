# 前端 / UI 規劃：Railway 免費試用部署

## 介面範圍

- 目標系統介面：`線上登入及記帳頁面介面`。
- 需求來源：試用規格 FR-001～003、SC-001；兩人以測試資料驗證 Google 登入、帳號隔離、旅行與支出，包含手機及內頁重新整理。
- 上游依據：本 package 的 `spec.md`、`research.md`、`plan.md`、`truth-delta.md`；現有前端 auth、trip、expense feature/DSL 與 OpenAPI。
- 結論：產品 UI 行為與視覺設計沿用現有實作。新增 `/healthz` 是部署就緒端點，不屬使用者畫面；data truth 與既有業務 API 均 NOOP。此次需要的是線上環境驗證，沒有新增畫面、元件、互動或文案的設計需求。

## 視覺方向

- 風格來源：現有 `apps/web/src` 的旅帳介面與既有設計系統。
- 本次風格結論：沿用現有版面、字體、色彩及手機響應式行為；此輪不修改視覺方向。
- 視覺重點：驗收時確認線上資源完整載入，手機登入與記帳畫面可用，沒有部署造成的樣式或靜態資源缺失。

## 畫面與流程

| 現有畫面 | 現有入口 | 試用驗證 | 錯誤與狀態 |
| --- | --- | --- | --- |
| Google 登入 | `/`、`Login.tsx` | 兩個實際 Google 帳號分別登入；核對 HTTPS、回呼與登入後導頁 | 登入中、取消、回呼錯誤、網路失敗；不能顯示未授權帳本 |
| 旅行清單 | `/trips`、`Trips.tsx` | 登入後只見自己資料；手機建立測試旅行 | 載入、空清單、查詢或儲存失敗依既有狀態呈現 |
| 旅行帳本 | `/trips/:tripId`、`TripLedger.tsx` | 檢視該旅行與幣別總額；重新整理和直接開啟內頁 | 無權限或不存在的資源不可顯示他人資料 |
| 支出表單 | `/trips/:tripId/expenses/new`、`ExpenseForm.tsx` | 建立測試支出、確認金額與幣別；手機可操作 | 驗證、儲存中、失敗與結果未確認，沿用既有回饋 |

現有 `App.tsx` 使用 BrowserRouter，私有路由在無 session 時導回登入入口。伺服器端 SPA fallback 須讓內頁可載入，但 `/api` 未知路徑與缺失資源不可被改寫為首頁回應；這是部署路由驗證，不是新 UI 設計。

## 互動、狀態與資訊揭露

- 既有產品資料及互動：沿用現有登入、旅行、支出和權限行為；兩個帳號的測試資料只在各自帳本顯示。
- 平台資訊：額度、部署狀態、環境變數及備份操作寫在管理者 runbook，不加入旅帳產品畫面。
- 錯誤回饋：沿用現有登入失敗、查詢失敗、表單驗證與結果未確認狀態；部署後逐一驗證。若線上環境暴露現有 UI 無法表達的真實錯誤，再記錄具體缺口並交回相應規格流程。
- 無障礙與響應式：以既有鍵盤操作、標籤、錯誤文字及手機版面作回歸；至少一次實機手機驗證，不能以桌機截圖替代。

## 靜態雛形輸出規劃

本輪無新產品 UI 狀態或流程，故不產出新的 `ui/*.html`。既有可運行介面及先前設計素材已可供 review；重畫相同畫面會製造另一份可能不同步的設計。此次驗收以真實部署、Google OAuth、手機、直接開啟內頁和 E2E 回歸作證據。若後續另有使用者可見流程變更，先更新此計畫，再按 skill 建立完整可操作雛形。

## 前端實作與驗收交接

- 前端產品元件預期 NOOP；部署建置需交付 Vite 靜態產物並由同 origin 服務提供。
- 對後端契約的依賴：既有 `/api/auth/*`、帳號／旅行／支出 API 不變；`GET /healthz` 僅供平台就緒檢查。
- 驗證重點：受影響的既有前端 Playwright BDD E2E、真實 Google 登入與取消、兩帳號隔離、手機建立旅行與支出、內頁重新整理／直接進入、缺失 JS/CSS 與未知 API 的回應。
- 後續 handoff：可進入 `/tasks` 編排工程交付；本輪未新增業務 UI 語意，既有前端 feature/DSL 可作回歸依據。若 `/dsl-refine` 執行，應先依 acceptance 與本輪 truth-delta 判斷 NOOP。
